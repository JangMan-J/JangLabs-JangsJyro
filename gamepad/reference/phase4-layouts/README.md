# Phase-4 diagnostic layouts

Three Steam Input VDF layouts for Phase-4 adversarial pin-traces.
All files here are **generated** — never hand-edited. The generator is
`tools/vdf_layout_gen.py`; every file is validated via a parse→emit→reparse
round-trip before being written to disk.

Regenerate:
```
python3 tools/vdf_layout_gen.py marker --dtt 190 --out reference/phase4-layouts/marker_layout.vdf
python3 tools/vdf_layout_gen.py release-press-isolated --out reference/phase4-layouts/release_press_isolated.vdf
python3 tools/vdf_layout_gen.py remove-layer  --out reference/phase4-layouts/remove_layer.vdf
python3 tools/vdf_layout_gen.py action-set-swap --out reference/phase4-layouts/action_set_swap.vdf
```

> **vdf-edit protocol reminder** (from `findings/steam_lane_behavior.md`):
> backup → edit autosave → `steam -shutdown` → relaunch nested env
> → canary slice → run.  Copy the desired layout from here over the autosave
> path; keep the original autosave backed up.

## `marker_layout.vdf` — Four-activator marker layout (gate-review spec)

**Generated by:** `python3 tools/vdf_layout_gen.py marker --dtt 190`

**Provenance:** gate-review respec (2026-06-11). Supersedes `marker_f13-f16.vdf`.

**Key map — invariants:**
- Every (button, activator) → unique F-key.  F1–F10 only.
- F11/F12 excluded: xinput aliases them to legacy L1/L2 keysyms.
- F13+ excluded: unproven binding tokens on this XI2 stack (Phase 2 only confirmed F1–F12).
- `interruptable` NOT set on the test button — Steam default throughout.

**Layout:**

`button_y` — THE test button, carries all four activator types:

| Activator | Binding | Behaviour (doc + oracle) |
|-----------|---------|--------------------------|
| `Start_Press` | F1 | Fires at press-DOWN, instantly deactivates (no hold state); in-stream pipeline-latency marker |
| `Release_Press` | F2 | Fires at press-UP; in-stream marker |
| `Full_Press` (Regular) | F3 | When double-bound: delayed to first-down + DTT=190 ms; held as state thereafter |
| `Double_Press` | F4 | Fires at second-down (d2d < DTT); DTT=190 ms explicit |

`button_a` — digital baseline / canary:

| Activator | Binding | Purpose |
|-----------|---------|---------|
| `Full_Press` | F5 | Unambiguous "am I live" pulse; no competing activators |

`button_b` — tap/hold pair:

| Activator | Binding | Purpose |
|-----------|---------|---------|
| `Full_Press` | F6 | Short-tap result |
| `Long_Press` | F7 | Long-hold result |

`button_x` — `interruptable=0` probe:

| Activator | Binding | Purpose |
|-----------|---------|---------|
| `Full_Press` (interruptable=0) | F8 | Fires regardless (alongside Long_Press) |
| `Long_Press` | F9 | Long-hold result |

**Why in-stream markers matter (pipeline latency ~35 ms):**
F1 (Start_Press) and F2 (Release_Press) appear in the same XI2 capture stream as
F3/F4.  The injector timestamp alone only pins "DTT + unknown offset"; the in-stream
markers let pipeline latency cancel:
- `F3_t − F1_t` ≈ DTT (pipeline offset cancels)
- `F4_t − second_down_t` ≈ 0 ms (direct second-down latency)

**Findings / Oracle predictions being pinned:**

1. **Pin #1 — Regular (F3) emission at first-down + DTT=190 ms:** single press on
   button_y → F3 must appear at first-down + 190 ms (±poll-slack), regardless of
   hold/release time. → `vary_hold_d2d_pin.txt`, `singles_anchor_set.txt`
2. **Pin #2 — Double (F4) at second-down:** d2d < 190 ms → F4 at second-down, ~zero
   latency, F3 suppressed. → `double_emission_timing.txt`
3. **Pin #3 — Held-double output shape:** second press held past first-down + DTT; no
   spurious F4 at the DTT boundary (retracted re-send clause). → `held_double_watch.txt`
4. **Start_Press / Release_Press new-primitive characterization:** F1 at DOWN, F2 at UP;
   side-channel on every probe; both activator types are **not yet A-B traced** (no JSM
   counterpart run yet). Converter equivalence pending trace evidence.

## `release_press_isolated.vdf` — Release_Press discrimination layout

**Generated by:** `python3 tools/vdf_layout_gen.py release-press-isolated`

**Provenance:** Phase-4 batch-1b follow-up (2026-06-12). Runner observed F2
(Release_Press) absent on `marker_layout.vdf`'s button_y across all probes.
F2 absent at the raw layer — not a delivery/flush issue. Two candidates:
(a) bad VDF token; (b) Full_Press or Double_Press activator suppresses Release_Press.

**Key map — invariants:**
- Every (button, activator) → unique F-key.  F1–F7 only.  No F11/F12 (L1/L2 aliases).
- F13+ excluded.  All keys unique.  Round-trip validated.

**Layout:**

| Button | Activators | Bindings | Discrimination question |
|--------|-----------|---------|------------------------|
| `button_a` | `Release_Press` ONLY | F1 | Token good? → isolated Release_Press, no co-activators. If F1 is absent: bad token. If F1 fires: interaction is the cause. |
| `button_b` | `Start_Press` + `Release_Press` | F2 + F3 | Does Start_Press suppress Release_Press? |
| `button_x` | `Full_Press` + `Release_Press` | F4 + F5 | Does Full_Press suppress Release_Press? (suspected blocker per batch-1b) |
| `button_y` | `Double_Press` (DTT=190) + `Release_Press` | F6 + F7 | Does Double_Press suppress Release_Press? |

**Discrimination logic (runner):**

| Observation | Conclusion |
|-------------|-----------|
| button_a (F1) silent | Bad token — `Release_Press` activator unrecognized by Steam; all other Release_Press buttons will also be silent |
| button_a fires F1 | Token is good; interaction is the cause |
| button_a fires F1, button_x (F5) silent | Full_Press is the blocker |
| button_a fires F1, button_y (F7) silent | Double_Press is the blocker |
| button_a fires F1, button_b fires F3 | Start_Press does NOT block Release_Press |

**Note:** `button_x` (Full_Press + Release_Press) is the **high-priority** probe
because the batch-1b four-activator button had Full_Press co-present. Test this
pairing first.

## `remove_layer.vdf` — Timed remove_layer layout

**Generated by:** `python3 tools/vdf_layout_gen.py remove-layer`

**Binding format (EMPIRICALLY VERIFIED — 130+ real configs, vdf/ corpus):**
```
"controller_action add_layer <preset_id> 1 0, , "
"controller_action remove_layer <preset_id> 1 0, , "
```
LayerA has preset id=1; binding references this numeric id. Args `1 0` (majority observed;
`1 1` also seen in v13; semantics unconfirmed — `1 0` used, record uncertainty here).

The layout also declares an `action_layers` block at controller_mappings top level:
`"LayerA" { "set_layer" "1"  "parent_set_name" "Default" }` — mirrors real corpus structure.

**Layout (F1–F10 only):**

| Button | Set | Binding | Purpose |
|--------|-----|---------|---------|
| `button_a` | Default (base) | F1 | Canary — always active in base set |
| `button_b` | Default (base) | F2 | Base binding, overridden by layer |
| `button_x` | Default (base) | `controller_action add_layer 1 1 0` | Applies LayerA |
| `button_y` | Default (base) | `controller_action remove_layer 1 1 0` | Removes LayerA |
| `button_b` | LayerA (id=1) | F3 | Layer override of F2 |

**Findings served — Phase-4 `remove_layer` gotcha:**

1. **Layer activation:** press button_x; then button_b → must emit F3 (layer override active).
2. **Layer removal timing:** while in LayerA, press button_y; then button_b → must emit F2 (base resumed). Key question: does removal happen at press-DOWN or press-UP of button_y?
3. **Timed remove:** drive `down X` → `wait <N>ms` → `down Y` → check button_b output. Sweep N to find the minimum stable window.
4. **Base canary throughout:** button_a (F1) should fire in all states.

> **Arg pair uncertainty:** `1 0` vs `1 1` semantics unconfirmed from corpus. If add/remove
> layer silently fails, try `1 1` and report what works.

## `action_set_swap.vdf` — Two-action-set swap layout

**Generated by:** `python3 tools/vdf_layout_gen.py action-set-swap`

**Binding format — ⚠ UNVERIFIED-HIGH-RISK HYPOTHESIS:**
```
"controller_action change_preset <preset_id> 1 0, , "
```
No real-config or documentation evidence found for this verb. The tokens
`change_action_set` / `change_preset` from docs turned out to be screenshot
filenames. `change_preset` is the lead hypothesis based on `controller_action`
verb patterns in the real corpus (add_layer, remove_layer, hold_layer).

**Runner diagnostic:** press START; if button_a still emits F1 instead of F3, the
verb is wrong. Report the exact binding string from a GUI-saved action-set-swap layout.
This layout is **not on the critical-path trace scripts** — treat as exploratory.

**Layout (F1–F10 only):**

| Button | Set Default (id=0) | Set SetB (id=1) |
|--------|-------------|----------|
| `button_a` | F1 | F3 |
| `button_b` | F2 | F4 |
| `START` | `controller_action change_preset 1 1 0` | `controller_action change_preset 0 1 0` |

**Findings served — Phase-4 action-set swap:**

1. **Correct set active:** before any swap, button_a → F1; after START press, button_a → F3.
2. **Switch timing:** does the swap happen at START press-down or release? Drive `down START` → `up START` → `press A`; compare F3 timestamp vs START-down timestamp.
3. **Round-trip swap:** Default → SetB → Default; confirm F1 and F3 alternate correctly.
4. **Converter classification:** Steam action sets have no direct JSM analogue; expected verdict `requires_user_choice` or `unsupported_omitted`. This trace produces the evidence.
